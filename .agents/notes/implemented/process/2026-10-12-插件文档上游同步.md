# Agent Note: 插件开发文档与上游同步取增量——本仓库本地增补不回流、不被覆盖

Status: implemented
Class: process

## 背景

`docs/插件开发/` 的 5 份规范是本仓库对 Spark 主仓库（`D:\demo\test01\spark\插件开发\`）的副本。
本仓库在副本上做了**单向本地增补**：页面加固 §12（WebView / Native）、`插件开发规范` §12 安全约束第 6 条
与 §9.2 的调试入口说明、`插件市场与仓库` §6.1 现状说明 + §6.2.1 提交完整性核对 + `MrHan-Yd/master` 实际地址。
2026-10-12 逐份对拍证实**上游从来没有这些内容**：上游 `git log -S"页面加固"` 无输出、上游工作区
文件里也没有——差异纯属本仓库单向多出来的。

风险因此很具体：同步时若拿上游文件整体覆盖，会静默删掉 §12 与 §6.2.1，而 AGENTS.md §3 正把
`WebView插件开发.md §12` / `Native插件开发.md §12` 当作代码模板指向它，15 个已发布插件的加固实现
也会失去文档依据。

## 决策

**同步 = 只摘上游增量，本地增补原样保留。** 做法是逐份 `diff`，把上游新增的实质条目按本文件自身行尾
（Native / 规范 CRLF，WebView / 签名 / 市场 LF）做纯文本外科替换，绝不整文件覆盖。

2026-10-12 本轮上游增量只有一条：**「插件名（`name` 子串）隐式搜索入口」**，落在三份文档 8 处——
`插件开发规范` §5 隐式入口段 + §5 路由契约（四类入口顺序与按 plugin_id 去重）+ §10 native 入口表述；
`WebView插件开发` §1 与 §5；`Native插件开发` §0 两条与 §0 特性表行。对应上游实现
`crates/plugin-manager::find_name_matches`（名称包含、忽略 ASCII 大小写、空输入不产候选、无 page feature 不产候选）
与 `crates/host::search_core` 的四类入口 `taken` 去重（精确 > 前缀 > 插件名 > regex/root）。

本轮无需改动的：`插件市场与仓库.md`（上游那份是通用模板，本仓库已本地化，无上游新增内容）、
`插件签名规范.md`（与上游逐字节相同，md5 一致）。

## 放弃方案

1. **直接 `cp` 上游文件覆盖。** 最强理由：一步到位、不可能漏条目；但会静默删除 §12 页面加固与 §6.2.1，
   AGENTS.md §3 的模板链接随即断链，且属于「无提示的功能倒退」——覆盖后没有任何地方记录被删了什么。
2. **把本地增补回流上游。** 最强理由：单一真源，以后无需 diff；但上游是 Spark 主仓库（本仓库之外的项目），
   改它超出本仓库边界；且 §6.2.1 的 `git ls-files` 条数核对是本仓库特有的发布纪律（源自 local-search 的 exe、
   pdf-toolkit 的 179 个 cmaps 实际漏提交），对上游无意义。

## 代价与后果

收益：上游新能力（照插件名搜到插件）进入本仓库文档；本地增补不被覆盖，AGENTS.md 链接保持有效；
两份副本的「谁有谁没有」有了明文台账。代价：每次同步必须人读 diff，不能机械复制；两份副本长期漂移属必然，
保留项靠本笔记与 AGENTS.md §3 判断。若日后上游也补进页面加固，应收敛为一份并合并表述，而不是二选一。

本轮（2026-10-12）在无宿主会话中完成（`SPARK_TRACE_SESSION` 为空），故不挂 `@trace`，本笔记即留痕本身。
