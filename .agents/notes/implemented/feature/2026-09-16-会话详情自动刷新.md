# Agent Note: 会话详情自动刷新（轮询探针）
Status: implemented
Class: feature

## 背景
看板的会话详情是一次性快照：`loadSession` 读一次 `events.jsonl` 后缓存在 `session.events`，
之后点同一个会话走的都是缓存，页面里没有任何轮询/监听。用户使用 agent 干活时，trace 文件
边跑边追加，看板却永远停在打开那一刻的数据——「正常使用 agent 的时候，tab 里的数据要跟着长」
是明确的用户预期，死快照没有意义。

规范侧此前只有「宿主每轮会话结束重建索引、看板随时并发读」（SPEC §5.8）与实时模式的
WebSocket 审批/轨迹通道（§7.2），归档模式下没有任何自动更新条款。

## 决策
会话详情进入后启动 3 秒轮询（`app.js` 的 `startPolling`），每 tick 用 events.jsonl 全文**文本
长度**做探针（`source.js` 的 `probeEventsLength`）：与上次基线（`S.pollLastLen`）相同就跳过本轮，
变了才重读解析、重建 model、重渲染详情。状态栏在每次实际刷新后带「自动刷新 HH:MM」时间戳；
探针失败静默跳过本轮，不打断轮询。

配套不变量与生命周期：
- **`session.events` 非空 ⇔ 事件内联在会话条目里**（bundle/粘贴源）。文件源不再把解析结果写回
  `session`——写回会让轮询分不清「内联死数据」和「上一轮缓存快照」，`loadEvents` 因此天然
  承担了「内联走缓存、文件走重读」的分叉，不再需要单独的 `reloadEvents`。
- 轮询生命周期四点收口：切会话（`loadSession` → `startPolling` 重拉）、切模块
  （`setModule` 离开 session 即 `stopPolling`）、换数据源（`loadFrom` 入口 `stopPolling`）、
  页面隐藏（`document.hidden` 跳过 tick，`visibilitychange` 回前台补一枪）。
- 重读结果过 `S.loadToken` + `S.session !== session` 双闸，与点会话的时序闸共用同一套令牌。

## 放弃方案
事件条数当探针基线（第一版实现）：把 `readText` 返回的**字符长度**与 `S.events.length` 比，
两个量纲永远不相等，等于每 tick 必重读，探针形同虚设——实测自查抓出来的，改为维护
`S.pollLastLen` 文本长度基线后才真正「没变不动」。

WebSocket 实时通道（SPEC §7.2 实时模式）：需要宿主常驻、看板常连，归档模式的立身之本就是
「不需要任何后端」；为「tab 跟着长」引入一条长连接协议，断线重连、半开连接的故障面都压在
看板上，而轮询 3 秒一次、没变化时零解析零渲染，对目录/路径/远程三种 Reader 一视同仁。
它最强的理由是「真实时」，但 trace 的消费节奏是回看与巡查，3 秒延迟完全够用。

文件监听（fs.watch / FileSystemObserver）：宿主能力面只有 `spark.fs.read/write`，插件页没有
watch API；要支持得先给宿主加能力、动权限模型，为一个看板功能不划算。

`session.events` 写回 + 单独 `reloadEvents` 强制重读（第一版实现）：能跑，但「有缓存」从此
有了两种含义（内联 vs 上轮快照），每个调用点都要人脑判断该不该绕缓存；改为「文件源永不回写」
后，`loadEvents` 的分叉只看数据形态，不看调用动机，错配面直接消失。

## 代价与后果
收益：agent 会话进行中，看板时间线/改动/合规/被否决跟着磁盘数据长，打开 tab 即可旁观执行
全程；没变化时每 tick 只有一次文本读，无解析无渲染。

代价：每 3 秒一次全文 `readText`（大 trace 是 MB 级文本拷贝；本地可忽略，HTTP 远程模式会多
出流量）；状态栏新增「自动刷新」时间戳，按旧文案精确匹配的断言会破（现测全过）；会话结束后
轮询空转到用户切走为止，每 tick 只剩一次读，可接受。
