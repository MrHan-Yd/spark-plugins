# Agent Note: 看板新增「文件档案」模块——按文件聚合运行事实
Status: implemented
Class: feature

## 背景
看板原有五个模块全是「会话维度」：按会话看、按规则看、按笔记看。用户最自然的第一个问题——
「这个文件为什么变成现在这样？」——没有入口：要知道答案得自己在多个会话间翻时间线、拼 diff。
数据其实早已备好：digest 里的 `heavy_files`（写盘）、`denied`（被拦，目标从 parent 解出）、
`compliance_failed`（合规未过）三路聚合原料齐备，缺的只是消费视图。

## 决策
新增第六个顶部模块「文件档案」（`trace-board/0.1.0` 的 `aggregate.fileArchive` + `modules.renderArchive`）：
一个文件一行档案——涉及会话数、落盘次数、被拦次数、合规未过数；有被拦/合规未过的排前，
再按落盘次数。点「展开档案」看该文件的三路明细（落盘 / 被拦被拒 / 合规未过），每条明细可点回
所在会话详情。纯前端消费 digest，schema 零变更、零 N+1（HTTP 远程模式安全）。

## 放弃方案
复用「架构基线」的承重墙块：承重墙只统计落盘（heavy_files），没有被拦与合规维度，且它承担的是
「决策知识 KPI」叙事，塞进运行事实查询会把两个回答不同问题的视图搅在一起。最强的理由是少一个
tab，但「文件档案」回答的是**单文件深查**，承重墙回答的是**全局改动面**——粒度不同，合并就是
两头不讨好。

把 denied/compliance 也并进 `heavy_files` 的字段（宿主侧改 digest schema）：破坏性 schema 变更
要 bump 版本、老索引全废，而看板聚合层用 `targetLabel` 归一后按 rel 合并完全够用。不动宿主、
不弃老索引，两全。

## 代价与后果
收益：agent 改动的每个文件有了完整「档案页」——谁改的、被拦过几次、合规挂没挂过，一处可查。
代价：digest 的 denied/compliance_failed 有条数上限（60），大库下档案可能不完整（界面上有
「统计范围」约束，可接受）；顶栏页签从五个变六个，宽度略涨。
