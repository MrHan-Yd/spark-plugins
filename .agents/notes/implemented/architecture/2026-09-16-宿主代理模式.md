# Agent Note: 宿主代理模式——让直开的客户端会话也过宿主链路
Status: implemented
Class: architecture

## 背景

追溯宿主的留痕模型是 opt-in：只有宿主亲自拉起的 agent 会话才有协议事件流。直开的客户端会话
（ZCode 直接启动 agent）不经 host.mjs，看板零事件——2026-09-16 一整天的 trace-board 改动就是
这样裸奔的。反向锚点条款因此改为条件式（见 [条件式反向锚点](../process/2026-09-16-条件式反向锚点.md)），
但那只是诚实降级，不产生事件；owner 拍板「agent 改的都要记录」，直开会话必须上链路。

## 决策

host.mjs 增加 `--proxy`：宿主对外伪装 agent（外层 client 的 stdio 直连本进程），对内仍以 client
身份拉起真 agent，双向转发、双向落盘。dir 沿用 `client->agent`/`agent->client`（代理透明，看板
schema 零改动）；反向请求（权限/fs/terminal）就地处理不外泄——审批闸门、合规评估、快照/Diff 全部
生效；唯一加料点是 session/new 注入 `_meta.sparkTrace` 并以 `proxy/session_new_mutated` 披露；
代理模式下宿主 stdout 是协议通道，人话日志强制走 stderr；默认 `--policy allow`（纯记录），显式
`--policy ask` 仍可人工审批。一个代理进程 = 一个追溯会话，随外层 client 断开 / agent 退出 / SIGINT
统一收尾。契约测试 `.agents/runner/tests/proxy-test.mjs`（17 项：转发零污染、就地拦截、注入生效、
收尾落盘）。

## 放弃方案

1. **转发型代理**（反向请求也转发给外层 client，宿主只旁观记录）。最强理由：最透明、宿主职责最小、
   审批 UI 天然复用外层 client 的；但审批闸门/合规/快照全部失效，宿主退化成抓包器——留痕有了，
   治理没了，与宿主存在的意义（可拦截）冲突。
2. **客户端 hook 桥**（用 ZCode 的 hook 把工具调用写成 trace 事件）。最强理由：零侵入、不要求
   客户端支持自定义 agent 命令；但事件语义弱（无审批流、无 stopReason）、绑定特定客户端、格式要
   二次映射，且 hook 事件本质仍是客户端自报而非协议观测。留作 ZCode 配不了 agent 命令时的备选。

## 代价与后果

收益：直开会话的事件流从零到全量，`@trace` 前提永远成立，「agent 改的都要记录」闭环。代价：多一跳
进程（stdio 转发，延迟可忽略）；代理进程生命周期与外层 client 绑定（client 崩了会话即收尾）；
外层 client 必须支持把 agent 启动命令配成本代理，否则此路不通（ZCode 能否配置由 owner 验证，
配不了则回退 hook 桥方案）。
