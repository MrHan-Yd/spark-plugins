# Agent Note: 看板数据源库持久化加 localStorage 兜底
Status: implemented
Class: bug-fix

## 背景
owner 实测：看板里添加的数据源（项目）刷新后全部丢失，连「最近使用」列表也清零。
排查发现数据源库只写 `spark.db`（WebView插件开发.md §6.5，落盘 `plugin-data/<id>/db`），但
`libSave` 把写失败静默吞掉（旧注释「存不下不影响本次使用」），`libLoad` 读空也不提示——
宿主 db 不可用或写失败时整条链路无声失效，界面上毫无痕迹。ui-smoke 的 db 桩是内存 map，
真实宿主的落盘行为零覆盖。同仓库 time-converter / hw-ladder 的偏好存储早已是
「spark.db 优先 + localStorage 兜底」双写，看板是唯一单通道的页面。

## 决策
数据源库与主题统一改双通道：写 `spark.db` + localStorage（`trace-board:` 前缀）双写；
读 db 优先、读不到（null / 抛错 / 非数组）回落 localStorage。会话内发现 db 写失败后
（`dbBroken`）连读也绕开 db，防写挂的陈旧 db 库把 localStorage 里更新的数据盖回去。
最近一次入库的实际落盘通道经 `lastSaveMode()` 暴露：数据源库抽屉与启动状态栏如实披露
（`local`＝db 不可用、暂存 localStorage；`none`＝两条通道都挂、本次不保留）。

## 放弃方案
只加「存储失败 toast」不加兜底通道。它改动最小，但提示解决不了丢数据本身，
浏览器预览（无宿主）场景依旧什么也记不住；双写是同仓库已验证的既有模式，边际成本更低。
另一候选是改用 File System Access API 存目录句柄，能免重选，但宿主内核支持度未实测，
风险与工作量大，且解决不了「库本身刷新即丢」这个更根本的问题。

## 代价与后果
库在两条通道各存一份，体积翻倍（库条目是小元数据，粘贴数据已封顶 5 条，可接受）；
双通道短暂分叉时以 db 为准读，可能读到一瞬陈旧列表，下一次双写自愈。
theme 写 db 的 fire-and-forget 补了 `.catch`，db 写拒绝不再产生未捕获异常。
验证：ui-smoke 新增「db 与 localStorage 双写同数据」「db 读空时 libLoad 回落」两条断言，
外加「注入 db 全挂桩 → reload → 自动恢复上次来源与库列表」的真实刷新路径（截图 12）。
